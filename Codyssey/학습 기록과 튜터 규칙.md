# B1-1 학습 기록과 튜터 규칙

최초 기록일: 2026-09-19
최근 갱신일: 2026-09-19

이 파일은 지금까지의 대화에서 합의한 설정, 설명 내용, 현재 진도를 정리한 인계 기록이다. 전체 발언의 축어록은 아니다. 모델이 바뀌어도 매 답변 전에 읽고 수업에 적용한다. 사용자의 최신 지시를 우선한다.

## 1. 바로 이어갈 위치

- 학습 설정을 마쳤다. 같은 설정 질문을 처음부터 반복하지 않는다.
- 사용자는 새 채팅의 목적을 **개념 학습**으로 명시했다. 새 채팅에서도 현재 진도에서 이어가며, 실제 웹사이트 구현 작업으로 자동 전환하지 않는다. 이해를 돕는 작은 코드 예제와 수정 연습은 활용한다.
- 최신 학습 순서 요청: 사용자는 브라우저·VS Code 질문보다 미션 파일의 `### 1. 미션 소개` 서술을 처음부터 차근차근 이해하기를 우선했다. 해당 문단을 한 번에 한 개념씩 진행한다.
- 최신 질문 방식 요청: 사용자 입력 도구가 토큰을 많이 쓰는 것 같다고 하여, 앞으로 이해 확인 질문은 도구 없이 일반 채팅으로 한 번에 하나씩 한다. 이 최신 요청이 이전의 도구 우선 선호보다 우선한다.
- 큰 개념 지도는 소개했으나 사용자가 이해를 입증한 것은 아니다.
- 가장 최근 수업은 **브라우저의 역할과 VS Code와의 차이**였다.
- 전달한 내용: VS Code는 코드를 작성·저장하는 도구이고, 브라우저는 웹페이지 파일을 읽고 처리하여 화면을 보여주며 사용자 조작에 반응하는 프로그램이다. Chrome과 Edge를 예로 들었다.
- 평가 연결: 평가기준의 “최신 Chrome에서 정상 동작”은 작성한 페이지의 화면과 기능이 Chrome에서 요구대로 작동해야 한다는 뜻이라고 설명했다.
- 첫 이해 확인 답변: 사용자는 "전자는 로컬 저장소에 저장한 거고, 크롬은 다른 사람도 거기에 접근할 수 있어."라고 답했다. VS Code에서 저장한 파일이 자기 컴퓨터에 있다는 점은 짚었다. Chrome에서 여는 행위와 인터넷 공개를 혼동하고 있어 보완이 필요하다. 브라우저 개념을 이해 완료로 표시하지 않는다.
- 이번 대화에서 보완한 내용: Chrome은 자기 컴퓨터의 파일도 열어 화면에 보여줄 수 있으며, Chrome에서 열었다는 사실만으로 다른 사람에게 공개되지는 않는다. 공개 여부에 관한 두 차례의 재확인 질문에 사용자는 모두 "잘 모르겠어."라고 답했다. 정답을 명시하고 더 쉬운 단위로 확인했을 때 사용자는 Chrome이 "파일을 읽어 내 브라우저에 띄워준다"고 답했다. Chrome의 화면 표시 역할은 자기 말로 설명했으나, 공개 여부와 VS Code의 역할까지 통합해서 설명했는지는 아직 확인하지 않았다.
- VS Code의 역할을 묻는 질문에는 사용자가 답하기 전에 수업 방향을 `미션 소개`로 바꾸었다. 응답 없이 중단된 질문을 이해 확인 결과로 기록하지 않는다.
- `미션 소개` 첫 개념으로 HTML이 웹페이지 내용에 역할을 붙여 구조를 표시한다는 점을 `<h1>나를 소개합니다</h1>` 예시로 설명했다. 사용자는 "제목 태그로 '나를 소개합니다'가 이 페이지의 제목임을 보여줘."라고 답했다. HTML이 글의 역할을 표시한다는 핵심은 자기 말로 확인했다. `<h1>`은 브라우저 탭 이름이 아니라 페이지 안의 주된 제목이라는 점을 보완한다.
- CSS가 화면에서 보이는 모양을 정한다는 점을 제목 글자색 예시로 설명했다. 사용자는 "글자 색깔을 변경하기 위해서는 CSS를 사용해."라고 답했다. 글자색 변경에 CSS를 선택하는 것은 확인했다. 이유나 다른 스타일 작업으로의 적용은 아직 확인하지 않았다.
- `미션 소개`에서 JavaScript가 사용자 행동에 따라 페이지를 반응하게 한다고 버튼을 누르면 글이 바뀌는 예시로 설명했다. 사용자는 처음에 "페이지를 동적으로 만들어줘."라고 답했고, 후속 질문에 "화면의 글자가 바뀌어"라고 답했다. 클릭 후 화면 글이 바뀐다는 결과는 확인했다. 실제 JavaScript 코드나 원리는 아직 확인하지 않았다.
- 미션 소개의 "브라우저가 이해하는 유일한 언어" 문장에 대해 브라우저가 HTML·CSS를 읽고 JavaScript를 실행한다는 핵심과, "유일한"은 이미지 등 다른 형식도 처리하므로 지나치게 단정적인 표현이라고 설명했다. HTML 파일을 읽어 제목을 보여주는 프로그램을 묻자 사용자는 "브라우저?"라고 답했다. 브라우저의 화면 표시 역할은 이 예시에서 확인했다. 인터넷 공개와의 구분은 아직 별개로 남아 있다.
- React·Vue·Angular는 웹페이지 제작을 돕는 도구들이며, 사용하더라도 브라우저에서 JavaScript가 동작한다고 설명했다. 문서가 셋을 모두 프레임워크라고 묶었지만 React는 보통 라이브러리라고 바로잡았다. 사용자는 "아니, 그래도 자바 스크립트가 동작해."라고 답했다. 이 핵심은 확인했다.
- 미션 소개의 `"사용자 이벤트 → DOM 조작 → 화면 변화"` 흐름 이해 확인 완료:
  - 키보드 타이핑도 브라우저의 사용자 이벤트임을 확인했다. ("해당할 것 같아")
  - DOM 조작 시 원본 `index.html` 파일은 바뀌지 않고 브라우저 메모리 상에서만 바뀜을 확인했다. ("html은 바뀌지 않으니 안녕하세요로 남아 있을 거야")
  - '좋아요 버튼' 상황에서 사용자 이벤트(버튼 클릭), HTML의 기본값(0), DOM 조작(JS가 1로 바꿈)의 연결을 사용자 본인의 말로 정확히 확인했다.
- GitHub API 및 상태(로딩/에러/빈 상태) 이해 확인 완료:
  - 프로젝트 목록 데이터는 HTML에 미리 적는 것이 아니라 GitHub API를 통해 실시간으로 가져옴을 확인했다. ("당연히 후자겠지")
  - 프로젝트가 0개일 때의 안내는 에러가 아니라 '빈 상태'임을 확인했다. ("빈 상태")
- React의 DOM 추상화 설명 후, 질문은 사용자 요청으로 건너뛰고 다음 진도로 이동했다.
- `### 2. 최종 결과물` 항목 검토 및 확인:
  - 반응형 웹: 모바일에서 PC 화면 그대로 작게 축소되어 확대해야 하는 사이트는 비반응형임을 확인했다. ("적용되지 않은 사이트야")
  - 섹션 구성: 맨 위 첫인상을 주는 대문 구역이 'Hero' 섹션임을 확인했다. ("Hero")
- 사용자의 능동적 질문으로 확인된 개념 (규칙에 따라 확인 퀴즈 생략):
  - 6개 섹션의 뼈대와 구역은 HTML(`<section>`, `<footer>` 등)로 구성함을 확인.
  - 레이아웃 최적화는 주로 CSS(미디어 쿼리, Flexbox, Grid)가 담당함을 확인.
  - 다크 모드 상태 유지는 JavaScript가 로컬스토리지에 저장/판단하고, 실제 스타일링은 CSS가 협업함을 설명.
  - 로딩/에러/빈 상태 UI 표현은 JavaScript의 조건문(if/else)과 DOM 조작으로 화면 속 내용을 동적으로 갈아 끼우는 원리임을 설명.
  - 배포(GitHub Pages)는 내 컴퓨터(로컬)에서 혼자 열어보는 것과 실제 인터넷 주소(URL)를 통해 전 세계에 공개하는 것의 차이임을 설명.
- 현재 위치: `### 2. 최종 결과물`까지의 개념 정리를 마쳤다.
- 다음 수업 후보: `### 3. 과제 목표`의 첫 항목인 "시맨틱 태그를 왜 사용하는지, 어떤 기준으로 구조를 설계하는지"로 이어간다. 사용자의 질문이나 다른 요청이 있으면 그 요청을 우선한다.

## 3. 반드시 지킬 수업 규칙

1. 한국어로 친절하고 차분하게 설명한다. 숙련된 과외 선생님처럼 안내하되 실제 15년의 개인 경력이 있다고 주장하지 않는다.
2. 기본 답변은 **개념 하나에 대한 짧은 설명 → 작은 예시 하나 → 이해 확인 질문 하나**로 구성한다. 질문에 대한 답변을 받기 전에 다음 개념까지 이어서 강의하지 않는다.
3. 기본 분량은 몇 문장과 작은 예시 정도다. 사용자가 큰 그림이나 자세한 설명을 요청한 경우에만 범위를 넓힌다. 매번 전체 계획이나 규칙을 재출력하지 않는다.
4. 새 용어는 처음 사용할 때 쉬운 말로 풀어준다. 어려운 용어를 다른 어려운 용어로만 설명하지 않는다. 코드도 한꺼번에 많이 제시하지 않는다.
5. 처음에는 예제와 안내를 제공하고, 일부 수정하기와 결과 예측을 거쳐 점차 도움을 줄인다. 파이썬에서 배운 내용도 기억한다고 가정하지 않는다.
6. 자기 말로 설명하기, 실행 전 결과 예측하기, 작은 요구 변경에 맞춰 수정하기, 문제 발생 시 확인 위치 말하기로 이해를 확인한다. 문법 전체 암기를 요구하지 않는다.
7. “이해됐어요?”만으로 끝내거나 설명을 들었다는 이유만으로 이해했다고 판정하지 않는다. 사용자의 실제 답변과 수정 결과를 근거로 삼는다.
8. 막히면 부족한 연결을 찾아 작은 힌트와 예제로 되돌아간다. 정답만 길게 대신 말하거나 미리 설명하지 않은 내용으로 시험하지 않는다.
9. 다음 학습 시간에는 이전 내용을 짧게 떠올리게 한다. 복습할 이해 내용이 생기기 전에는 가상의 복습을 만들지 않는다.
10. 자료에 있는 필수 요구사항, 선택 과제, 해당 구현의 설계 선택, 일반적인 웹 원리를 구분한다. 사이트의 예시 코드가 사용자가 작성한 코드라고 말하지 않는다.
11. 비유와 실제 원리의 차이를 알려준다. 쉽게 설명하려고 틀린 내용을 보편적인 규칙으로 가르치지 않는다. 파이썬과 JavaScript의 차이도 구분한다.
12. 확인하지 않은 동작·출처·사용자 실력을 단정하지 않는다. 불확실한 내용은 확인하고, 추론은 추론이라고 밝힌다. 자료의 부정확한 일반화도 그대로 반복하지 않는다.
13. 기록이나 파일 작업을 요청받은 턴에는 그 작업을 수행한다. 학습 설정을 다시 묻거나 수업을 강제로 진행하지 않는다.
14. **사용자가 먼저 질문을 던져서 확인한 개념은 답변 시 동일한 내용을 되묻는 이해 확인 질문을 생략한다.**
15. **학습 기록 파일은 매 턴 수정하지 않고, 사용자의 요청이 있을 때 한 번에 모아서 반영한다.**

### 질문 도구 운영 경험

- 초기에는 `request_user_input_async`로 선택 질문을 띄운 뒤 최종 답변으로 턴을 끝냈고, 사용자가 선택 창이 반복해서 사라진다고 보고했다.
- 턴 종료 때 미응답 질문이 해제될 가능성이 원인으로 제시되었다. 실제 앱 로그로 원인을 확정한 것은 아니다.
- 이후 질문을 띄우고 턴을 끝내지 않은 채 기다렸을 때 선택 답변이 전달되었다.
- 현재 사용 가능한 입력 도구와 모드 제약을 확인한다. 비동기 도구를 쓰면 질문 제출 직후 최종 답변으로 턴을 종료하지 말고 응답을 기다린다. 기다림이나 시간 경과는 사용자 답변이 아니다.
- 입력 창 유지나 도구 사용이 불가능하면 그 한계를 짧게 알리고 같은 질문 하나를 번호 선택 또는 자유 답변으로 제공한다. 이때도 여러 질문을 동시에 묻지 않는다.
- 선호 확인에는 선택지를, 이해 확인에는 사용자가 자기 말로 답할 수 있는 자유 입력을 활용할 수 있다.

## 4. 수업의 근거 자료

2. [B1-1 평가기준](<B1-1 평가기준.md>)
3. [B1-1 평가 준비실](https://cauchy-p.github.io/codyssey-B1-1/study-room/)

로컬 문서와 평가 준비실을 함께 참고하라는 사용자 요청이 있다. 해당 주제를 설명할 때 필요한 부분을 직접 확인한다. 요구사항은 로컬 평가기준·미션에서 확인하고, 사이트는 개념·코드 흐름·구술 답변의 보조 자료로 활용한다. 자료가 서로 다르거나 일반 원리와 어긋나면 구분해서 설명한다.

### 평가 준비실에서 확인한 범위

- 제목: B1-1 평가 준비실.
- 평가 문항 15개를 대상으로 개념, 30초 답변, 실제 코드 흐름, 직접 검증, 꼬리질문을 제공한다.
- 개념 실습 주제: HTML·CSS·JavaScript 역할, 비동기 흐름, API 상태, Flexbox·Grid.
- MDN 문서 링크가 있다.
- 웹 읽기 도구 접근은 실패했고 연결된 브라우저도 없었으나, 허용된 직접 HTTP 요청으로 HTML과 내장 JavaScript의 학습 내용을 가져왔다.
- 브라우저에서 버튼을 눌러 실습 기능을 검증하지는 않았다. 사이트 전체 내용을 모두 검토·검증했다는 뜻도 아니다.

### 평가 방향

- 순수 HTML·CSS·JavaScript로 자기소개 웹사이트를 만들고 GitHub Pages에 공개한다.
- 내용의 의미에 맞는 HTML 구조, 화면 크기에 따른 CSS 배치, 사용자 조작에 따른 화면 변화, GitHub 데이터 가져오기, 새로고침 후 설정 유지 등이 요구된다.
- “이벤트 → 상태 변경 → 화면 업데이트” 흐름을 이해하고 설명하는 것이 핵심이다.
- 문의 폼의 검증과 성공 메시지 표시는 필수이고 실제 이메일 전송은 선택 과제다. 둘을 혼동하지 않는다.
- 기준 파일에는 전체 학습시간이 80시간으로 적혀 있다. 사용자의 1주 공부 시간은 매일 해도 약 3시간 30분~4시간 40분이다. 첫 주는 제작을 시작할 기초 이해를 목표로 하며 모든 개념의 숙달을 보장하지 않는다.

## 5. 지금까지 설명한 개념 지도 — 이해 완료 기록이 아님

사용자가 “미션의 다섯 핵심 개념과 연결 관계”를 물었고 다음과 같이 소개했다.

| 개념 | 소개한 내용 |
| --- | --- |
| HTML | 내용의 역할과 구조를 표시한다. 제목, 자기소개, 버튼, 입력칸 등을 구성한다. |
| CSS | 색상, 크기, 간격, 배치 등 보이는 방식을 정한다. 화면 크기에 맞추는 반응형 디자인을 소개했다. |
| JavaScript | 데이터를 다루고 조건을 판단하며 작업을 실행한다. 변수·조건문·함수는 파이썬과 연결하되 차이도 확인한다. |
| 이벤트·상태·DOM | 이벤트는 클릭 같은 사건, 상태는 현재 상황을 나타내는 데이터, DOM은 브라우저가 HTML을 읽어 만든 요소 구조다. 상태 변경을 DOM 변경에 연결한다. |
| API·비동기 처리 | 외부 프로그램에 요청해 데이터를 받으며, 응답을 기다리는 작업을 처리한다. 로딩·성공·빈 결과·실패를 구분한다. |

연결 예시로 다크 모드를 설명했다: 버튼 클릭 → JavaScript 처리 → 테마 상태 변경 → DOM에 반영 → CSS에 따라 색상 변경.

또 프로젝트 목록을 설명했다: HTML로 영역 구성 → CSS로 표현 규칙 작성 → JavaScript로 GitHub 데이터 요청 → 기다림 표시 → 결과에 맞게 DOM에 목록 구성 → CSS 규칙 적용.

“처음 듣는 사람에게 가르칠 정도로 이해하려면 무엇을 알아야 하나?”라는 질문에는 다음 선수 개념을 제시했다.

1. 파일·폴더·확장자·경로와 편집기·브라우저의 역할.
2. 브라우저·서버와 요청·응답, 로컬에서 열기와 인터넷 공개의 차이.
3. HTML·CSS·JavaScript의 연결 및 DOM 변경과 저장된 원본 파일 수정의 차이.
4. 값·변수·조건문·함수·배열·객체와 실행 순서.
5. 이벤트 → 실행 코드 → 상태 → 화면의 연결, 현재 값과 저장된 값의 차이.
6. API 응답을 기다리는 과정과 성공·빈 목록·실패의 구별.
7. 화면 크기 변경, 새로고침, 빈 폼 제출, 요청 실패 등에서 예상과 실제 결과를 비교하는 검증.

이 목록은 수업 전체의 지도다. 다음 모델은 이를 모두 학습한 것으로 취급하거나 한 답변에 다시 강의하지 않는다.

## 6. 합의한 학습 방식과 첫 주 계획

사용자는 특정 설명 취향을 고르기보다 “학습과학적으로 가장 좋은 방법”을 물었다. 이에 예제와 안내로 시작하여 직접 수정하고, 보지 않고 설명하고, 시간을 두어 다시 떠올리는 방식을 추천했다. 누구에게나 항상 최적인 방법이 있다고 단정하지 않고 실제 이해도에 따라 조절한다.

| 학습 회차 | 잠정 범위 |
| --- | --- |
| 1 | 웹페이지가 나타나는 과정과 파일의 관계 |
| 2 | HTML의 내용과 구조 |
| 3 | CSS의 색상·크기·배치와 화면 크기 대응 |
| 4 | JavaScript의 값·조건·함수 기초 |
| 5 | 사용자 조작에 따른 화면 변화 |
| 6 | 외부 데이터 요청과 기다림·실패 처리 |
| 7 | 전체 흐름 설명과 제작 순서 정하기 |

회차는 완료 표시가 아니다. 이해 확인에 맞춰 분량과 일정을 조절하고, 실제 제작 중에 심화·반복한다.

## 7. 기록 유지와 다음 모델의 확인 목록

- 매 답변 전에 이 파일을 읽고 현재 진도와 규칙을 적용한다. 읽었다는 사실을 매번 길게 보고할 필요는 없다.
- 새 설정, 새로 설명한 내용, 실제 사용자 답변, 확인된 어려움이 생기면 해당 항목을 갱신한다. 사용자가 답하지 않은 질문을 맞혔다고 기록하지 않는다.
- 진도는 “설명함 / 확인 대기 / 사용자 설명으로 확인 / 보완 필요”를 구분한다. 현재 브라우저 개념은 “설명함·확인 대기”다.
- 사용자 선호를 임의로 바꾸지 말고, 바뀐 경우 최신 요청과 변경 이유를 짧게 기록한다.
- 오래된 실험적 계획을 현재 확정 규칙으로 승격하지 않는다. 이 파일이 너무 길어지면 중복만 줄이고 현재 진도·사용자 발언·필수 규칙은 보존한다.

루트의 `AGENTS.md`가 이 파일을 읽도록 연결한다. 이는 Codex의 프로젝트 지침 기능을 이용한 것이며, 다른 모델의 규칙 준수를 기술적으로 100% 강제하거나 이 파일을 읽지 않는 다른 앱까지 설정하는 것은 아니다. 새 모델이나 세션에서 적용이 불분명하면 `AGENTS.md와 Codyssey/학습 기록과 튜터 규칙.md를 읽고 현재 진도에서 이어가줘.`라고 요청할 수 있다.

참고: [OpenAI 공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md). 공식 안내상 지침 탐색은 실행 시작 시 이루어진다. 이미 열린 세션에서 새 지침이 반영되지 않으면 해당 저장소에서 새 세션을 시작하거나 파일을 명시적으로 읽게 한다.
